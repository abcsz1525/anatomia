## Совместная работа с двух устройств

Этот репозиторий редактируется через Codex на двух компьютерах. GitHub (`origin`)
— общий источник сохранённых изменений. Не считайте локальную копию актуальной
без проверки. Следуйте этим правилам автоматически, без дополнительных просьб
пользователя о синхронизации.

### Перед изменением файлов

1. Проверьте `git status --short`, текущую ветку и её upstream. Выполните
   `git fetch origin` и сравните локальную ветку с удалённой.
2. Если рабочее дерево чистое и у ветки есть upstream, выполните
   `git pull --ff-only`. Если upstream отсутствует, проверьте `origin/main`
   и удалённую ветку с тем же именем; не назначайте upstream наугад.
3. Если есть незакоммиченные изменения, сначала изучите их. Не выполняйте pull,
   переключение ветки, автоматический stash или очистку поверх чужой работы.
   Сохраните её на месте; при необходимости ведите новую задачу в отдельном
   worktree от актуального `origin/main`.
4. Если история разошлась, не применяйте reset или принудительный push.
   Изучите обе стороны и интегрируйте изменения обычным merge с сохранением
   коммитов. При неоднозначном конфликте требований спросите пользователя.
5. Если fetch не удался, сообщите, что актуальность копии не проверена.
   Не представляйте такую копию как синхронизированную и не публикуйте изменения
   до успешной синхронизации.

### Во время работы

- Новые задачи ведите в отдельных ветках `codex/<краткое-имя-задачи>` от
  актуального `origin/main`. Для параллельных задач используйте разные ветки.
  Продолжая уже начатую задачу, сохраняйте её ветку и сначала синхронизируйте её.
- Перед редактированием перечитывайте файлы; не записывайте поверх свежих
  изменений устаревшую версию из контекста чата.
- Не отменяйте чужие изменения и не удаляйте незнакомые файлы. Не используйте
  `git reset --hard`, `git clean`, force-push или переписывание опубликованной
  истории без отдельного явного разрешения пользователя.
- При конфликтах сохраняйте смысл изменений обеих сторон; не выбирайте
  автоматически целиком `ours` или `theirs`.

### Перед передачей работы другому устройству

1. Проверьте diff и выполните проверки, соответствующие изменению. Добавляйте
   в коммит только файлы своей задачи, не включайте секреты и чужую работу.
2. Снова выполните `git fetch origin`. Интегрируйте новые коммиты удалённой
   ветки задачи и `origin/main`; после интеграции повторите затронутые проверки.
3. Завершённую работу закоммитьте и отправьте в ветку задачи обычным push
   (для новой ветки — `git push -u origin <ветка>`). Если push отклонён из-за
   новых коммитов, снова fetch, интеграция и проверки; никогда не force-push.
4. Убедитесь, что локальный HEAD совпадает с удалённой веткой, и сообщите
   пользователю имя ветки, коммит и оставшиеся локальные изменения, если они есть.
   Если публикация не удалась, явно скажите: другое устройство работу ещё не получило.

### Продакшн

Push в `main` автоматически запускает деплой на Railway. Сохранение работы
на GitHub делайте через ветку задачи. Слияние и push в `main` выполняйте только
после явного разрешения пользователя на публикацию этой задачи. Перед слиянием
обновите `origin/main`, сохраните изменения второго устройства и проверьте
результат интеграции. Не переносите разрешение на деплой прошлой задачи на новую.
